# Безопасность данных и восстановление

Текущая реализация `0.1.0-dev`, сверено 2026-11-03. Этот документ описывает гарантии
кода и пределы восстановления, а не результат проверки конкретных носителей M4.

## Граница записи

| Объект | Допустимое действие | Условие |
| --- | --- | --- |
| Существующий пользовательский оригинал | Чтение для просмотра, превью, сверки или копирования | Нельзя заменять, переименовывать, перемещать и удалять средствами нынешних операций |
| Новая обычная копия | Создание отсутствующих файлов и папок | Сохранённый план, просмотр, отдельный старт, проверка связи и корней |
| Новая копия Photos | Создание свободных конечных имён оригинальных ресурсов | Привязанная папка, явный запрос либо ранее включённое расписание |
| .media-actu-volume.json | Создание ID и изменение имени носителя | Явная регистрация/переименование, проверка идентичности |
| .media-actu-folder.json | Создание и обновление собственного описания папки | Зарегистрированная область, проверка владельца маркера и ревизии задания |
| Собственные временные файлы | Создание, публикация и ограниченная очистка | Проверенное имя и совпадающий identity |
| SQLite, журналы, JPEG-кэш, нативные сборки | Рабочая запись приложения | Только в настроенные каталоги приложения |

Поэтому формулировка «приложение целиком только на чтение» устарела. Гарантия
сохранности существующих пользовательских файлов остаётся, а служебные маркеры
являются отдельно разрешённой записью и могут обновляться фоном.
Решения: [ADR-0002](adr/0002-read-only-first-version.md), [ADR-0004](adr/0004-copy-missing-only.md),
[ADR-0005](adr/0005-photos-libraries.md), [ADR-0007](adr/0007-photos-buffered-direct-write.md).

## Защита путей и носителя

Относительные пути проверяются на абсолютность, NUL и `..`. Основные операции томов
читают через `open_readonly`: O_NOFOLLOW, проверка типа и st_dev, сверка маркера
сменного носителя до и после работы. Подмена точки монтирования не должна
незаметно перенести доверие на другой диск. Повреждённые или повторяющиеся ID
дают неподтверждённость и блокировку живых операций, а не потерю сохранённой истории.

Код: [`open_readonly`](reference/media_manager--comparison.md#symbol-open_readonly),
[`verify_identity`](reference/media_manager--volume_identity.md#symbol-verify_identity),
[`StorageCatalog.refresh`](reference/media_manager--storage.md#symbol-StorageCatalog.refresh).
Старая модель folder-источников использует отдельные проверки Path.resolve;
различия реализации перечислены в [документации файловых операций](development/data-and-files.md).

## План и запрет замены

План обычного копирования фиксируется по завершённому файловому отчёту. Перед
стартом и во время работы проверяются связь, источник, корни и версии исходников.
Существующие цели пропускаются, конфликты и отличающиеся размеры не исправляются
автоматически. Даже конкурентно появившаяся цель не должна заменяться.

Локальная публикация использует исключительное переименование/ссылку. На сетевом
томе новый конечный файл создаётся с O_EXCL. Частичная прямая запись может остаться
видимой до окончания операции: её наличие и размер не доказывают готовность.
Она сохраняется в staging-журнале и получает «Копия не завершена».

Код: [`MissingCopyCatalog.plan`](reference/media_manager--copy_files.md#symbol-MissingCopyCatalog.plan),
[`MissingCopyCatalog._write_file`](reference/media_manager--copy_files.md#symbol-MissingCopyCatalog._write_file),
[`publish_exclusive`](reference/media_manager--copy_files.md#symbol-publish_exclusive).
Остановка сохраняет готовые результаты. После перезапуска обычная операция
становится interrupted: нужно заново сверить файлы и создать новый план.

## Photos: отдельные гарантии

Оригиналы PhotoKit передаются в Core, накапливаются в ограниченный буфер 64 МиБ и
пишутся сразу в новый конечный файл. До первого байта намерение записи сохраняется
в SQLite. После fsync и закрытия проверяются размер и идентичность через stat;
байты назначения повторно не читаются для SHA-256.

Квитанция связывает медиатеку, asset ID, resource ID, версию, путь и fingerprint.
Она ускоряет продолжение, но не является криптографическим доказательством
неизменности содержимого. Принятие уникального ручного файла по имени/размеру —
ограниченная эвристика. Для проверки содержимого обычных файлов есть отдельная
SHA-256-сверка, которую нельзя подменять подписью «имя и размер совпали».

Конечные незавершённые Photos-файлы не удаляются и не перезаписываются. Повторная
передача использует свободное имя. Журнал показывает incomplete_paths для ручного
разбора. Готовность Live Photo требует всех ресурсов объекта.
Код: [`PhotosOriginals._save`](reference/media_manager--photos_originals.md#symbol-PhotosOriginals._save),
[`PhotosOriginals._receipt`](reference/media_manager--photos_originals.md#symbol-PhotosOriginals._receipt),
[`PhotosOriginals.journal`](reference/media_manager--photos_originals.md#symbol-PhotosOriginals.journal).

## Что делать после сбоя

| Ситуация | Ожидаемое поведение | Действие |
| --- | --- | --- |
| Закрыт браузер | Core продолжает свои задания | Вернуться в UI и проверить сохранённое состояние |
| Перезапущен UI | Фоновые службы Core не затронуты | Открыть страницу; навигация восстанавливается из снимка вкладки |
| Прервано превью | running возвращается в pending | Проверить доступность кэша и очередь |
| Прервана сверка | Становится paused, индекс/история сохраняются | Продолжить либо начать новую сверку при изменившихся областях |
| Прервано обычное копирование | interrupted, готовые файлы остаются | Проверить журнал, заново сверить и создать план |
| Прерваны оригиналы Photos | paused, квитанции сохраняются | Проверить ту же медиатеку и папку, продолжить; расписание может продолжить ранее сохранённый запрос |
| Отключён том | Снимки остаются, живое состояние недоступно | Подключить тот же носитель и повторить проверку ID |
| Нет внешнего кэша | Не используется скрытый запасной системный путь | Подключить настроенный том либо явно изменить конфигурацию |
| Кончился диск назначения | Работа ждёт/завершается ошибкой с журналом | Освободить место вручную, изучить незавершённые пути и продолжить подходящим сценарием |
| Не записан маркер папки | Задание остаётся pending/error для повтора | Проверить доступность, путь, владельца маркера и состояние очереди |

Не удаляй staging-записи из SQLite только ради красивого прогресса: они удерживают
информацию о незавершённых конечных файлах. Не считай disconnected или offline
доказательством отсутствия данных. Порядок диагностики: сохранить базы → изучить
состояние/журнал → подтвердить ID томов и пути → выбрать продолжение или новую сверку.

## Резервное копирование данных приложения

Ценные данные: оба SQLite-файла с согласованными WAL-данными, связи, квитанции,
история, локальная конфигурация и нужное состояние UI. JPEG и собранные helper
производны и могут быть пересозданы. Резервная копия одних JPEG не восстанавливает
связи и историю; копия каталога не является копией пользовательских оригиналов.

Для ручного копирования баз останови записывающие службы и переноси согласованный
набор файлов либо используй корректный SQLite backup. Простое копирование только
`.sqlite3` из работающего WAL-каталога может потерять незачекпоинченные изменения.
Автоматического универсального backup/restore-интерфейса в проекте нет.

## Чего пока нет

Нет общего карантина, плана отката изменения оригиналов, обратимого удаления,
автоматического восстановления структуры и политики гарантированного количества
независимых проверенных копий. Записанное решение remove/move в отчёте — только
плановая отметка, не выполненное удаление/перемещение.

Будущие операции над существующими файлами должны получить отдельную модель плана,
подтверждения, журнала, проверок и восстановления до исполнения. Их требования
сохранены в [roadmap](roadmap.md); нынешние операции нельзя описывать как уже
обладающие универсальным откатом.
