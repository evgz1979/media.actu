# Photos: PhotoKit, транспорт и оригиналы

## Разделение ответственности

`SystemPhotosAdapter` — Python-клиент. `photos_adapter/main.m` — Objective-C-приложение
с AppKit/PhotoKit в GUI-сеансе пользователя. Helper получает разрешение macOS,
читает объекты Photos, миниатюры и оригинальные ресурсы. Core владеет каталогами,
целями записи, квитанциями и прогрессом. Helper не получает путь назначения оригинала.

[`SystemPhotosAdapter.ensure_built`](../../media_manager/photos_adapter.py#L93) собирает app-bundle
в `data/native/media-actu-photos.app`, копирует Info.plist и выполняет ad-hoc codesign.
Изменение main.m или Info.plist вызывает пересборку по mtime. Разрешение Photos и
право scripting-открытия объекта относятся к GUI-сеансу M4; они не выдаются кодом
документации и не проверяются одним успешным unit-тестом.

## Unix-сокет и несколько клиентов

На macOS клиент запускает app через `/usr/bin/open -g -n`, без передачи пользовательских
параметров назначения. Endpoint пользователя —
`/private/tmp/media-actu-photos-v2-<uid>/photos.sock`; каталог должен принадлежать UID,
быть настоящим каталогом и иметь 0700. Helper создаёт файлы под umask 0077 и принимает
только клиентов с тем же UID, проверяемым getpeereid.

[`serveDefaultSocket`](../../photos_adapter/main.m#L489) удерживает flock service.lock, очищает
устаревший endpoint только как его владелец и запускает сервер.
[`serveSocket`](../../photos_adapter/main.m#L442) обслуживает подключения независимо; один
клиент закрывает свой канал, а не весь helper. Без клиентов служба завершает работу
после 30 секунд простоя, поддерживая NSRunLoop для PhotoKit.

У Core два экземпляра адаптера: для превью/проверок и для оригиналов. Это два
клиентских канала одной службы. Не-GUI режим через stdin/stdout остаётся доступен
и используется fake-helper в тестах; его нельзя считать неиспользуемой ветвью.

## Фрейминг и ошибки

Транспорт — UTF-8 JSON, один объект на строку. `_buffer` хранит байты после первой
полной строки. [`SystemPhotosAdapter._receive`](../../media_manager/photos_adapter.py#L287)
ограничивает размер ответа и ждёт готовности канала через selector.
Одноразовые запросы сериализуются RLock клиента.

| Ответ helper | Исключение клиента | Смысл |
| --- | --- | --- |
| not_determined / denied / restricted | PhotosAccessDenied | Нужен доступ macOS |
| unavailable / library_mismatch | PhotosLibraryUnavailable | Медиатека недоступна или другая |
| cloud | PhotosThumbnailPending | Локальной миниатюры пока нет |
| cancelled | PhotosTransferStopped | Кооперативная остановка |
| error | PhotosAdapterError | Остальная ошибка helper |
| Истёкший срок чтения строки | PhotosResponseTimeout | Нет полного ответа за отведённое время |

Преобразование: [`SystemPhotosAdapter._check_response`](../../media_manager/photos_adapter.py#L313).
Транспортный сбой закрывает канал. `_request` не выполняет скрытый полный экспорт
или неограниченный повтор операции после ошибки.

## Короткие операции

[`handleRequest`](../../photos_adapter/main.m#L199) обслуживает:

- `authorize`: запрос системного разрешения и возврат его статуса.
- `probe`: count, до 12 распределённых sample ID и matched переданных identifiers.
- `scan`: список id/name/kind/created_at фото и видео по creationDate.
- `guard`: проверка доступа, доступности и якорей перед потоком оригиналов.
- `thumbnail`: локальный JPEG, ограниченные размеры, без разрешения сетевой загрузки оригинала.

Якоря требуют не менее `min(3, count)` найденных ID. В Python
[`matches`](../../media_manager/photo_libraries.py#L24) использует такой же порог при сопоставлении
профилей. Если ровно один прежний профиль пуст и ещё не индексирован, он может принять
первую медиатеку. Наполненные профили требуют доказательств идентичности; неоднозначное
совпадение не объединяет каталоги автоматически.

`photos://system` сохраняется для прежней записи, новые профили получают
`photos://<library_id>`. `photos-<source_id>` — отдельное UI-представление, не адрес
пакета `.photoslibrary`. Пакет медиатеки напрямую не открывается.

Версия JPEG-кэша и версия оригинального ресурса различаются. В обычном `scan`
helper передаёт created_at; `Catalog.replace_photos_scan` записывает эту дату
в media_files.modified_at (при отсутствии даты использует время скана).
Ключ Photos-превью строится из ID и этого поля. Манифест оригиналов отдельно
использует assetVersion по modificationDate. Поэтому версия ресурса оригинала
сама по себе не доказывает автоматическую инвалидацию уже готового JPEG после
редактирования объекта. Это ограничение текущего кода, а не новое поведение.

## Манифест оригиналов

[`originalRequest`](../../photos_adapter/main.m#L324) сначала выполняет guard, затем отправляет
`event=begin, protocol=2, pid=...`. Для `op=original_manifest` перечисляет также скрытые
объекты (`includeHiddenAssets=YES`). Это отличается от обычного scan, где этот флаг
не задан. На каждый подходящий объект выдаётся событие asset:

```json
{"event":"asset","asset":{"id":"asset-id","version":"...","name":"IMG_0001.HEIC","created_at":"...","resources":[{"id":"1:0","type":1,"name":"IMG_0001.HEIC","uti":"..."}]}}
```

Выбираются типы исходных ресурсов 1, 2, 3, 4 и 9: фото, видео, звук, альтернативный
RAW и движение Live Photo. `originalResources` сортирует по типу, имени и UTI;
`resourceID` добавляет порядковый номер внутри типа. Версия объекта строится из
modificationDate либо creationDate с шестью десятичными знаками времени.

Завершение: `event=complete,count=...`. Core обновляет ресурсы по asset/resource и
поколению seen. Только успешный полный манифест удаляет прежние невстреченные строки.
Прерванный манифест не должен обнулять старый прогресс.

## Поток одного ресурса

Запрос `original_resource` содержит identifier, resource_id, version, anchors и token.
Helper проверяет наличие объекта, версию и ресурс, затем разрешает сетевую загрузку
только для получения оригинала. События:

1. `begin` — поток принят после guard.
2. `progress` — дробь системной загрузки, не чаще примерно раза в 0,5 секунды.
3. `chunk` — base64 данных, до 256 КиБ декодированных байтов.
4. `complete,size` — общее переданное число байтов после повторной проверки версии.

Python декодирует base64 с validate=True и проверяет непустой блок и предел 256 КиБ.
Срок неактивности потока — 300 секунд. Чтение опрашивается с шагом 0,25 секунды;
при остановке отправляется `cancel` с token, после 5 секунд ожидания отмены клиент
прерывает свою сторону. Ошибка callback-потребителя тоже закрывает канал, прекращая
ненужную передачу после отказа диска. Код:
[`SystemPhotosAdapter._stream_request`](../../media_manager/photos_adapter.py#L341).

Системный progress загрузки, число принятых байтов, буферизованные байты и записанные
байты — разные величины. UI не должен считать fraction=1 доказательством fsync и
готовой квитанции файла.

## Манифест, квитанции и запись Core

[`PhotosOriginals.run`](../../media_manager/photos_originals.py#L744) проверяет привязку и корень,
индексирует stat назначения, принимает манифест, восстанавливает готовность, затем
сохраняет оставшееся. До новой загрузки ресурсы уже известных копий имеют приоритет.
Готовые квитанции сопоставляются по ID ресурса, версии и параметрам файла.

`_save` может повторно принять квитанцию, передать готовый ресурс из peer либо
запросить PhotoKit. Названия приводятся к безопасному UTF-8, обычная структура —
`YYYY/YYYY-MM` или `Без даты`. При peer сохраняются его относительная папка и имя.
Коллизия имени получает свободный суффикс; существующая цель не заменяется.
Запись и гарантии разобраны в [данных и файлах](data-and-files.md).

## Цепочки копий

`photos_copy_sources` хранит ребро назначение → источник. Нет ребра — прямой Photos.
`root_copy` поднимается по цепочке и обнаруживает циклы. `start` зависимой копии
перенаправляет работу к корню. `_replicate_all` обходит доступных потомков в порядке
зависимостей и копирует только подтверждённые готовые ресурсы upstream.

Репликация выполняется перед основной работой, каждые 256 ресурсов и в конце.
Ошибка зависимого назначения сохраняет waiting и журнал; отсутствие готового
upstream не разрешает незаметно переключиться на Photos. У корня допускается
приоритетное восстановление из уже известных копий той же медиатеки.

[`PhotoLibraries.make_first_copy`](../../media_manager/photo_libraries.py#L319) меняет номера,
но не таблицу источников. Источники задаются `set_copy_source` отдельно.
`unbind_copy` помечает connected=0, не удаляя квитанции; зависимая маршрутизация
может после этого ожидать недоступный источник. Документация не должна обещать
автоматическое перенаподключение маршрутов при отвязке.

## Неиспользуемый scripting-путь

`open.applescript` действует для выделения объекта в Photos.
`_applescript_status`, `_applescript_scan`, `scan.js` и `export.applescript`
не входят в текущий путь получения превью/индекса. Старый export использует
`using originals false`: это экспорт производной версии, не нынешнее сохранение
оригинальных ресурсов. Все файлы сохранены, статусы и доказательства — в [реестре](../legacy.md).
